# A relation field and its foreign key columns: one key for last-write-wins

A factory whose definition holds `author: userFactory` accepts `create({ authorId: ada.id })` at compile time. Each layer is typed on its own, and each is a valid create input in isolation. Merging them key by key used to put `authorId` beside `author`, which fits neither of Prisma's input shapes, so the create failed with `Unknown argument 'authorId'`. Consumers reached for the column far more often than for the relation, and the typecheck stayed green every time. In Laravel the relation default _is_ the `user_id` attribute, so overriding one overrides the other.

The merge now treats a key-holding relation field and the columns of its foreign key as one key. Layers apply in their existing order: the definition, the states in the order applied, `for()` and `has()` layers in call order, then `create(overrides)`. A layer writing any column of the key drops the relation field an earlier layer wrote, whatever that field held: a factory, a row, or native relation input. A layer writing the relation field drops the columns an earlier layer wrote. "Writing" follows the existing skip rule: `undefined` writes nothing and drops nothing, and `null` writes. A column shared by two keys drops both relations. Within one layer nothing is dropped, and Prisma refuses a relation field beside its own column as it always has.

The pairing is read by `foreignKeyOf`, the inline-schema scan of ADR 0004 and ADR 0005. Where it has no answer, the field pairs with nothing and the merge is plain key-by-key, as before. That covers a client carrying no inline schema, and a declaration the scan cannot read. The metadata is read only when a layer holds a value that could stand in a relation field. A client carrying no metadata therefore still creates a model holding no relation.

The column then has to reach Prisma in a shape it takes. Where every key-holding relation field is filled by a fresh row, the create goes unchecked (ADR 0005), and the caller's columns are written as they are. Where the create stays on `connect`, a column set the caller named whole is rewritten into a `connect` on its relation field. The where-clause is built from the key's `references`, so `postFactory.state({ editor: grace }).create({ authorId: ada.id })` sends `author: { connect: { id: ada.id } }` beside `editor`'s connect. That where-clause holds the caller's value alone. It was never read off a row, so there is nothing that could have gone stale and no reason to widen the match. A key whose every column is `null` names no record, and is rewritten into the relation field's absence. A key named only in part, or only partly `null`, is left for Prisma to refuse.

## Considered Options

- Keeping the merge key by key and documenting the clash — rejected: the misuse type-checks, it is the most frequent one in consumer code, and a standing rule against it is only a convention.
- Refusing a column override at compile time where a layer before it holds the relation — rejected: no layer's type sees another layer, and Prisma's own input accepts the column.
- Dropping the relation only when every column of its key is written — rejected: a partly named compound key would still clash. Naming one column hands the whole key to the caller, who supplies the rest.
- Rewriting the caller's columns into a full-scalar `connect` — rejected: the caller handed over a key, not a row, and nothing beyond that key is known.
