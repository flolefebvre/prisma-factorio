# Compound unique keys: read off the inline schema the client carries

Connecting an existing row builds a `WhereUniqueInput` from its scalars, and for a model whose only unique constraint is compound — `@@id([a, b])`, `@@unique([a, b])` — Prisma demands the generated compound selector, `{ a_b: { a, b } }`, which no flat splat of scalars satisfies. `_runtimeDataModel` marks nothing unique (its fields carry `name`, `kind`, `type`, `relationName` and nothing further, per ADR 0002), and unlike arity there is no structural query-surface oracle to read the constraint through: ADR 0003's probe reads a yes/no off whether a fixed filter validates, but a compound selector's name surfaces only inside rendered validation-error text — which ADR 0003 already refuses to parse — its constituent fields surface nowhere at all once `name:` renames it, and probing candidate selectors structurally is combinatorial over field subsets while still missing every renamed one. The client does carry the schema it was generated from, whole, as `_engineConfig.inlineSchema` — the text its own query compiler executes against. `src/datamodel.ts` hands that text to `@prisma/get-dmmf` — Prisma's own parser, synchronous since v7, the library's one runtime dependency — whose DMMF names every constraint exactly: `primaryKey` and `uniqueIndexes` carry the constituent fields and the `name:` override, and `targetWhere` adds a compound selector for every constraint a row can name whole. The parse is all-or-nothing: a text the parser refuses — handed back as an error value, never a throw — yields no constraint for any model, leaving the flat scalars as they always were. A generated client never carries an invalid schema, its text having validated at generate time, so refusal reaches only a parser older than the schema's own syntax — the one degradation this trades for exactness, and it degrades to the old behaviour rather than inventing a selector that refuses a connect which works today.

This widens ADR 0002's "one internal API" reading to two internal surfaces, deliberately: both are read from `src/datamodel.ts` alone, so the confinement that keeps a shift in Prisma's surface a one-file fix stands. It does not reopen ADR 0001's rejection of parsing `schema.prisma` at runtime: that rejected the schema _file_ as a second source of truth beside the client, where the inline schema is the client instance's own copy, inseparable from the client it rides in on — still "runtime schema metadata comes from the client instance". A client carrying no inline schema — a hand-built double — degrades to the flat splat rather than throwing, for the same reason a scan miss does.

## Considered Options

- `Prisma.Args<…, 'findUnique'>['where']`, which does name the compound selector — rejected: type-level only, erased at runtime, so nothing to build the actual where-clause from.
- Reading the selector names out of a probe's `PrismaClientValidationError` message (`findUnique({ where: {} })` lists them) — rejected: message text is no contract, and even parsed it never yields the constituent fields behind a custom-named selector.
- A hand-rolled comment- and string-aware scan of the inline text for the two attributes — rejected: it owns a slice of Prisma's schema grammar in a library whose whole stance is inferring from what Prisma produces, tolerates text Prisma itself refuses, and answers approximately where the real parser answers exactly. The cost of exactness is accepted instead: the library's first runtime dependency, ~3 MB of WASM instantiated eagerly at import (~50 ms and ~24 MB of resident memory), itself a semi-internal toolchain package.
- An options-level `where` override on the row paths, or documenting the limitation with the native-input workaround (`{ connect: { a_b: { … } } }`, which still passes through untouched) — superseded: the metadata is recoverable, so the fix is transparent.
