# Relation field arity: read through the query surface, not off client metadata

A relation default declares whether the field it fills holds one record or many in its type alone, and a type cannot be read at runtime; `has()` never faces the question because calling it declares the arity outright. No metadata the client carries answers it either, in Prisma 7.8 — the options below record what was looked for. Guessing is ruled out because guessing wrong is silent rather than loud: a factory forced into a field holding a single record whose foreign key is required does not throw, it creates the child under a parent of its own to satisfy that key, and the `connect` then re-points the child, leaving a stray row standing. `holdsManyRecords` in `src/datamodel.ts` therefore reads arity through Prisma's public query surface: it issues `findFirst` under a relation filter only a field holding many records accepts — `some`, `every`, `none`, where a field holding a single record takes `is`/`isNot` or the target model's own where-input — and reads the outcome structurally, on `error.name === "PrismaClientValidationError"`, never by parsing message text. The probe names whichever of the three keys the target model declares no field under, and a target declaring all three throws rather than resolving to a guess: the relation filter on a field holding a single record accepts that model's full where-input, under which an empty scalar filter validates, so a fixed `{ some: {} }` probe against a target carrying a field named `some` would report "holds many records" and be believed. The answer is memoized per client in a `WeakMap` keyed by model and field; a rejected probe is evicted so a transient database failure does not poison the cache, a genuine database error is rethrown rather than read as an arity answer, and the probe fires lazily — only where a value actually needs an arity answer, never as a blanket lookup over the datamodel.

The cost, measured through Prisma's `$on("query")`: no query at all for a field holding a single record, which Prisma refuses client-side before it opens a connection; exactly one `SELECT … LIMIT 1` for a field holding many, and none thereafter on the same client. A transaction client handed over by `.using(tx)` is a different object, so it probes once per field of its own, for one extra select.

Two things follow from it. The library issues a read query of its own against the caller's database, which it did not before. And `findFirst` is a required delegate capability wherever a relation default stands: a hand-rolled test double carrying `create` alone no longer serves, and the error names the missing method and what it is read for rather than surfacing as a crash on a missing property.

## Considered Options

- A metadata signal on the client — rejected: there is none to read. In Prisma 7.8 the string `isList` appears nowhere in the generated client, the fields of `_runtimeDataModel` carry `name`, `kind`, `type` and `relationName` and nothing further, `client[model].fields` lists scalars and no relation field at all, and the generated `Prisma` namespace exports no `dmmf`.
- Parsing `client._engineConfig.inlineSchema`, which does carry the schema text at runtime — rejected: it answers arity exactly, but it is a second internal API where ADR 0002 confines the library to one, it reopens the runtime schema parsing ADR 0001 rejected, and it falsifies ADR 0002's reading of `_runtimeDataModel` as the only runtime source of relation metadata. ADR 0004 later adopts that surface for compound unique keys, which no query-surface probe can answer; the arity probe here stands.
- A `$extends` query override as a zero-query oracle — rejected: the override runs before Prisma validates arguments, so a field of either arity reaches it identically and it distinguishes nothing.
- Relation defaults taking rows and lists of rows but no factory where the field holds many records — rejected: it breaks the uniform attribute type PRD #26 settles on, under which a relation field accepts a factory, an existing row, or native Prisma relation input, with no qualifier on arity.
